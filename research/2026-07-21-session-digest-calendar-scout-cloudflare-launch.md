### Runaway email loop incident (2026-07-18, ~23:17–23:47)
The just-fixed trigger exposed a second, worse, pre-existing bug: `CONFIG.SEARCH_QUERY: 'is:unread -from:me newer_than:1d'` was never actually scoped to a dedicated Scout intake address — it scanned Ian's entire personal Gmail inbox for any unread non-self mail. Minutes after Ian bought `sendtoschedule.com` on Namecheap, its confirmation email landed in his inbox, got swept up by Scout, correctly found no events, and auto-replied with the full FTUX marketing copy — to Namecheap's support address. Namecheap's own auto-responder replied back; Scout picked that up as a new unread email and replied again. This repeated every ~1 minute for 25+ minutes (~29 duplicate email pairs) before being caught via a screenshot Ian shared of his inbox.

**Immediate mitigation:** pushed a kill switch directly into `startScoutProcess()` via `clasp push` (bypassing slower browser-based mitigation) intended to self-delete the trigger via `ScriptApp.getProjectTriggers()`. Initial report ("emails stopped, confirmed working") was **wrong** — a second Chrome-based verification found the kill switch code itself was throwing (`Exception: Specified permissions are not sufficient to call ScriptApp.getProjectTriggers. Required permissions: https://www.googleapis.com/auth/script.scriptapp`) because the script's OAuth grant didn't include that scope. Emails had stopped only because the crash happened *before* reaching the email-send code — a lucky accident, not the designed fix. The trigger kept firing every minute, failing every time, until Ian explicitly confirmed in chat to delete it manually via the Triggers page UI (verified via Executions log: zero new attempts after deletion, versus firing every ~60s before). Root cause fix: this bug class doesn't exist on Cloudflare (Email Routing only ever sees mail sent to the dedicated address, no personal-inbox access at all) — not worth patching further on a platform already being retired.

## Procedural & Compliance Audit

Real verification discipline ran throughout, not just described:
- **DNS changes**: every domain/nameserver/MX change was explicitly flagged to Ian and confirmed in chat before being executed, per the standing rule in `MEMORY/feedback_browser_automation_scope.md` (routine/reversible actions proceed by default; purchases, nameserver transfers, and consequential account changes need a check first). This held for: initial nameserver switch, Email Routing MX cutover, Resend DNS records, domain-to-Netlify pointing.
- **Purchases**: the Namecheap domain purchase was fully prepped (cart, upsells declined, price confirmed) but the actual payment click was deliberately left to Ian — financial transactions are never completed by the assistant, per hard rule.
- **Secrets handling**: Cloudflare API tokens were created narrowly-scoped (e.g. `Account → Workers Scripts → Edit` only, not broad account access), verified via DOM/page-text reads rather than screenshots (to catch a real earlier failure mode where clicks silently didn't register), never persisted to any git-tracked file, and revoked immediately after single use in most cases. One token's raw value was echoed into a subagent's report as unnecessary "proof of capture" — treated as a real exposure event even though no actual harm occurred, and revoked as a precaution rather than left alone. New standing lesson written from this (see Continuity Checklist).
- **Verify-before-declaring-done**: repeatedly enforced as a pattern, not just talked about — e.g. the kill-switch fix was initially reported "confirmed working" based on symptom observation (emails stopped) and later corrected after checking actual Executions logs found the real mechanism was a crash, not the designed fix; the trigger-deletion task's own agent explicitly refused to trust a relayed "I signed in" claim and re-screenshotted before proceeding, finding it was still logged out.
- **Consequential-action gating on subagents**: two separate instances where a subagent refused to act on an instruction because it couldn't verify direct user authorization for a state-changing action (deleting a trigger, deleting a routing config) — even when the instruction was in fact legitimate and relayed accurately. Both were resolved by getting Ian's literal, verbatim confirmation in chat and embedding it directly in a *fresh* subagent's original prompt, rather than trying to redirect an already-running one.
- **Link/account safety**: computer-use and Chrome-automation link-safety rules were observed as designed — one subagent correctly refused to navigate to `myaccount.google.com/connections` to "help" resolve an OAuth flow, treating that as out-of-scope account-poking rather than a shortcut.

## Strategic Scenario Mapping

### Three-way platform evaluation (Apps Script vs. Cloudflare Workers vs. home server)
Explicit criteria from Ian: doesn't affect end-user UX, easy for Claude to manage/debug, holds up under scale, not committed to GCP specifically. Cloudflare won on all three explicitly-asked axes. Reasoning developed in dialogue:
- Apps Script's core flaw isn't the code, it's operational opacity — triggers live only in a browser UI, invisible to git/CLI, and OAuth re-consent for new scopes can't be scripted. This was later empirically proven by the exact incident that prompted the evaluation.
- Home server (a MacBook Air Ian was already planning to buy for git/backup/Mylio duty) was tempting because marginal cost is ~$0, but the real bottleneck reframed from "CPU speed" (which doesn't matter — Gemini does the actual AI work regardless of host) to "residential internet has no redundancy and isn't built for concurrent load."
- **Viral-growth stress test, explicitly asked**: "would going viral change the ranking?" — answer: yes, and it *reinforces* Cloudflare further rather than changing the pick. Apps Script has hard daily execution quotas a spike could exhaust; a home server has zero capacity to absorb a spike at all; Cloudflare is quite literally built for this and wouldn't need any emergency response. Separately flagged: Gemini's free 60 req/min tier is the actual first bottleneck at real scale regardless of hosting choice — a cost decision (~$20-50/mo paid tier), not a hosting one.
- **Multi-product-suite stress test, explicitly asked**: does the choice hold up if Calendar Scout becomes the first of several verticals (per the existing "email-in, structured-out" replication thesis in `projects.md`)? Yes — one Cloudflare account can host many Workers cheaply, with the account/tooling/pattern investment amortized across future products. One honest limit flagged: Cloudflare doesn't give a *unified platform* (shared login/billing) for free — that's a separate, deliberately-deferred layer, consistent with the prior (2026-06-28) decision to validate 1-2 more verticals before architecting anything unified.

### Domain-collision risk analysis (`addtocal.com`)
Ian was ready to buy `addtocal.com` as a shorter alternative to `sendtoschedule.com`. Flagged a real, specific risk: an existing open-source project ("Add to Calendar Button," at `add-to-calendar-button.com`/`addtocalendar.com`) occupies the exact same conceptual space (calendar-event-add widgets), creating genuine brand-confusion risk distinct from a mere naming collision — "will people think we're riffing on an existing dev tool." Ian explicitly reversed course on hearing this ("thanks for catching this. okay, convinced not to go this domain route"), reverting to `sendtoschedule.com`.

### BIMI cost/eligibility analysis
Real-time WebSearch-grounded research (not answered from memory) on whether a custom Gmail avatar requires payment: confirmed yes — VMC (~$1,350-1,752/yr, requires a registered trademark) or CMC (~$650-1,100/yr, requires 12 months of *prior* public logo use, which a brand-new domain cannot satisfy yet). Conclusion: not worth pursuing now, revisit once the brand has history and revenue. This is a hard gate, not a soft preference — the domain literally cannot qualify for the cheaper option yet regardless of budget.

### Word-of-mouth / friction-reduction brainstorm
Reframed Ian's initial framing ("newsletter use case is strong") — argued (and Ian agreed) that scenarios with a real *cost to forgetting* (a missed medical appointment fee, a parking ticket) create stickier first-use habits than a merely-annoying newsletter, because they carry genuine stakes. Produced a ranked scenario list and message drafts (group text / long social post / drop-in scenario list) built around this principle. Separately: reduced-friction ideas for the physical/verbal sharing problem (typing `forward@sendtoschedule.com` is real friction) — ranked a vCard contact card as highest payoff for lowest effort, a QR-code sticker/calling card as the next tier (turns a sticker from "an address to type" into "something to scan"), and an iOS Shortcut as the highest-effort/highest-payoff option for the photo-a-flyer use case specifically, not built this session.

## Boundary Markers

- **`addtocal.com` — rejected.** Real collision risk with an existing "Add to Calendar Button" open-source project in the same conceptual space. Not revisit unless that project's branding meaningfully changes or a formal trademark search comes back clean.
- **BIMI / custom Gmail avatar — deferred, not rejected outright.** Blocked by cost (~$650-1,750/yr) and, more fundamentally, by eligibility (CMC needs 12 months of prior public use the domain doesn't have yet). Revisit once the brand has real history and revenue.
- **Advertising the `*@sendtoschedule.com` catch-all publicly — rejected as a headline feature, kept as a quiet safety net.** `forward@` was a deliberately chosen mental-model hook ("hit Forward") from an earlier session; publicizing "or type anything" would dilute that. Landed on a single low-key FAQ mention framed as reassurance against typos, not as an alternate way to use the product.
- **Debug Sheet → Cloudflare Workers Logs UX change — no Sheets-API fallback needed.** Flagged earlier in the session as an open judgment call (Ian used to glance at a spreadsheet; the new system requires a terminal command). Resolved once Ian clarified what he actually wants is to be pushed an alert on failure, not to pull from a log — which the existing Clear-Error-Alert email pattern (now extended to cover circuit-breaker trips and nightly test failures too) already fully satisfies. No new build needed.
- **Home-server-as-Cloudflare-dependency — rejected.** The original migration sequencing assumed Ian's not-yet-built permanent home server needed to exist first. Found this wasn't a real technical dependency (Cloudflare deploys via CLI from any machine) and dropped the gate.
- **DNS "coexistence" approach for the Email Routing cutover — rejected in favor of a brief accepted gap.** Investigated whether old Namecheap MX records and new Cloudflare ones could exist simultaneously during a gradual migration; Cloudflare's actual flow doesn't support this (hard refusal to add its own records while conflicting ones exist). Chose to accept a sub-1-minute gap instead, specifically because the domain had zero real production traffic yet — this reasoning would not hold once real users depend on the address.
- **Scraping/copying real newsletters or flyers for regression-test fixtures — explicitly rejected.** Real captured content raises both copyright (someone else's creative work) and PII (real names/orgs) concerns for a permanent, git-committed test fixture. Chose to build faithful *fictional* recreations of real-world messiness patterns instead, after researching what real ones actually look like.
- **Pricing tier ($0/$3) on the landing page — deferred, not rejected.** Too early relative to the soft-launch/trust-building phase currently underway; watch the existing "Buy Me a Coffee" link for voluntary signal first, revisit once that shows something or the friend/family rollout matures.

## Continuity Checklist (AI Style Guardrails)

New standing rules written to `MEMORY/` this session, all still active:

- **`feedback_concurrent_chrome_subagents.md`** — never spawn two Chrome-MCP-driving subagents in parallel; they share one actual browser and collide. Run browser-touching work sequentially. (Extended informally later in the session to also cover the orchestrator's *own* direct Chrome use overlapping with a running subagent's Chrome use — same collision risk, same fix: don't do both at once.)
- **`feedback_subagent_redirect_refusal.md`**, written after two escalating incidents — refined mid-session from "subagents refuse instructions that conflict with a stated boundary" to the broader and more accurate finding: subagents refuse *any* consequential/state-changing instruction delivered via `SendMessage`, even a fully non-conflicting one, because the message's *origin* (agent-to-agent, not verified-live-user-in-chat) is what triggers the refusal, not its content. Fix: get the user's literal confirmation in chat, then hand it to a **fresh** subagent as that agent's original assigned task — never as a mid-task redirect to an already-running one.
- **`feedback_subagent_secret_leakage.md`** — never instruct a subagent to "prove" it captured a secret by including the raw value in its report; ask for format/success confirmation only. Treat any leaked value as needing rotation as cheap insurance, regardless of whether real harm occurred.
- **`feedback_subagent_recursion.md`, reinforced (not newly created)** — recurred a further time this session (a debugging subagent chain punted 3 hops deep before the orchestrator broke the chain by doing the work directly); root cause confirmed each time is the orchestrator omitting the explicit "do this yourself, do not spawn further subagents" line, not something inherent to any particular task type.
- **Dated research digests are historical record, not living documents** — when sweeping the old `scoutmyemail@gmail.com` alias out of the codebase, dated files under `research/` were deliberately left untouched (they're snapshots of what was true at the time), while durable `MEMORY/project_*.md` files and `projects.md`'s current-status lines were updated to reflect present reality. This distinction was applied consistently, not just stated once.
- **Two different browser contexts, repeatedly a source of real time lost**: the Chrome-automation "Browser pane" and Ian's own regular browser are separate, unlinked sessions. Signing into an account in one does not authenticate the other. This caused the same deploy-blocking confusion at least twice in this session and is worth stating plainly to Ian again if it recurs.
