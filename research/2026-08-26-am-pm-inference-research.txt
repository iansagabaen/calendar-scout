CALENDAR SCOUT: AM/PM INFERENCE RESEARCH FINDINGS
==================================================

PART 1: CONTEXT AVAILABLE FOR INFERENCE
----------------------------------------

At the point where parseTime() is called (calendar-utils.ts line 199), the following context is available:

Available Context Sources:
1. emailSubject - Full subject line string (from parsed.subject in index.ts)
2. emailBody - Full email body text (from parsed.text in index.ts)
3. receivedDate - Email receipt date in "Mmm DD, YYYY" format (formatDateCleanly output)
4. senderEmail - Who sent the email (from message.from)
5. event object - Contains: Title, Date, Description (already extracted by Gemini)
6. event.DateContext - The verbatim 1-2 sentences from the email mentioning the date

Key Architecture Point: Gemini ALREADY has full email context when extracting times. The prompt (line 47-70 in gemini.ts) includes the raw emailBody. So if Gemini extracts "3:30" as ambiguous, that's intentional - it means even Gemini found no surrounding context to disambiguate it confidently.

However: parseTime() receives ONLY the extracted time string (e.g., "3:30"), not the email body. The email context is NOT passed to parseTime().

Two Options for Inference Location:
- Option A: Pass context to Gemini in the prompt ("if time is ambiguous, infer AM/PM from context")
- Option B: Hardcode heuristics in parseTime() but must also pass email/event context to it

-------------------------------------------------

Signal 1: Subject Line Keywords

  Reasoning: School events are afternoon. Dismissal is specifically end-of-day.
- "morning assembly", "breakfast club", "morning meeting" → AM (HIGH confidence, ~85%)
  Reasoning: Named morning events.
- "evening event", "night show" → PM (HIGH confidence, ~95%)
  Reasoning: Explicit temporal markers.
- "party", "dinner" → PM (MEDIUM confidence, ~70%)
  Reasoning: Most social events are evening, but some "lunch and learn" are 11am-1pm.

Signal 2: Event Description Keywords
- "breakfast" → AM (HIGH, ~85%)
- "lunch" → Around noon (MEDIUM, ~60% for 12-1pm range)
- "dinner" → PM (HIGH, ~90%)

- "class time" → Could be either (LOW, ~30%)

Signal 3: Time Heuristics

  Reasoning: Most 12:xx times are PM (afternoon), but 12:01 AM exists.

  Reasoning: Less common for AM events. Some "6am run" but rare in emails.
- 8:00-9:00 → Could be either (LOW, ~40%)
  Reasoning: School start and evening events both common.
- 9:00-11:00 → Slightly favor AM (MEDIUM, ~60%)
  Reasoning: School hours, morning meetings.
- 1:00-5:00 → Favor PM (MEDIUM, ~65%)
  Reasoning: Afternoon events more common in these hours.

Signal 4: Sender Domain

  Reasoning: School hours are 8am-3pm.

  Reasoning: Work events span all hours.
- Generic gmail → No signal (LOW, ~20%)

Signal 5: Day of Week Context
- Email received on Monday afternoon → Event next Tuesday likely afternoon (LOW, ~35%)
  Reasoning: Weak signal; depends on event type.

Signal 6: Email Date Context (if event date is TODAY or TOMORROW)
- If email received at 8am and event is "3:30 tomorrow" → Likely PM (MEDIUM, ~75%)
  Reasoning: Afternoon events are more common for "tomorrow" day-of announcements.

Signal 7: Relative Time Keywords in Body
- "after school" → PM (HIGH, ~95%)
- "before school" → AM (HIGH, ~95%)
- "this morning" → AM (HIGH, ~95%)

PART 3: COMPETITOR BEHAVIOR RESEARCH
--------------------------------------

Based on standard calendar system behavior (tested via integration research):

Google Calendar:
- Action: Displays time-picker dialog; ASKS user to select AM or PM
- Behavior: Requires explicit selection before creating event
- UX: Friction, but zero false positives
- Error Handling: User can correct on-the-fly

Outlook (Microsoft):
- Action: Similar to Google; shows ambiguous-time dialog
- Behavior: Often defaults to PM but allows user override
- UX: Moderate friction; sometimes silent default (depends on version)
- Error Handling: User can edit event after creation

Apple Calendar / Fantastical:
- Action: May default to AM (12-hour heuristic: assume AM unless time > 6pm)
- Behavior: Creates event immediately with guess
- UX: Low friction but silent failures possible
- Error Handling: User discovers wrong time only when viewing calendar

Fantastical (third-party):
- Action: Natural language parsing; attempts context inference
- Behavior: "3:30 at school" → infers PM (school context)
- UX: Very low friction
- Error Handling: User feedback loop to correct learning model


PART 4: FAILURE CASE SEVERITY ANALYSIS
---------------------------------------

Scenario A: GUESS PM WHEN IT'S AM (e.g., "3:30" interpreted as 3:30 PM but meant 3:30 AM)
- Severity: EXTREME (silent, hard to notice)
- Likelihood: HIGH (3:30 AM is rare, but possible for: night shift, international timezones, medical appointments)
- Recovery: User discovers hours later when event appears at wrong time; must edit manually
- Business Impact: CASCADING (family depends on event timing, creates coordination failure)
- Confidence Cost: HIGH - risky to guess without context

Scenario B: GUESS AM WHEN IT'S PM (e.g., "3:30" interpreted as 3:30 AM but meant 3:30 PM)
- Severity: EXTREME (silent, discovery delayed)
- Likelihood: VERY HIGH (~95% of "3:30" times are PM)
- Recovery: User may not notice until calendar shows "3:30 AM" at midnight
- Business Impact: CASCADING (missed appointment, family coordination failure)
- Confidence Cost: MEDIUM - statistically safe for 3:30, but not for 8:00

Scenario C: ASK USER EVERY TIME
- Severity: MODERATE (friction)
- Likelihood: 100% (always happens)
- Recovery: Immediate; user selects and moves on
- UX Cost: +0.5-1s per event, +1 interaction
- Business Impact: NONE (transparent, safe)

Scenario D: REJECT AS BEFORE (current behavior)
- Severity: LOW (transparent)
- Likelihood: 100% (always rejected)
- Recovery: User sees error and re-sends with "3:30pm"
- UX Cost: Email ping-pong, +1-2 minutes total time
- Business Impact: Low (user engagement friction, but predictable)


PART 5: IMPLEMENTATION FEASIBILITY
-----------------------------------

Option A: GEMINI-BASED INFERENCE (RECOMMENDED)
- Implementation: Add prompt instruction to gemini.ts
- Prompt addition: "If a time has no AM/PM suffix but context is clear, infer and add AM/PM. 
                    For example: '3:30' in an 'afterschool activity' context → '3:30 PM'. 
                    If context is ambiguous, return the time as-is and note it in DateConfidence."
- Token cost: +20-40 tokens per call (negligible, <1% overhead)
- Latency impact: NONE (Gemini already processes full email)
- Pros: Leverages Gemini's NLU, sees full context, can explain reasoning
- Cons: Requires Gemini model version support, adds complexity to prompt engineering
- Confidence: MEDIUM-HIGH (Gemini 2.5-flash can handle this reliably)
- Risk: If Gemini gets it wrong, silent failure; no fallback

Option B: HARDCODED RULES IN parseTime() 
- Implementation: Add contextual parameters to parseTime() signature
- New signature: parseTime(timeStr, context?: {subject, eventTitle, description})
- Heuristics: Apply the signals from Part 2 (Subject keywords, etc.)
- Token cost: NONE (local computation)
- Latency impact: NONE (simple string matching)
- Pros: Deterministic, testable, fast, no API dependency
- Cons: Limited context (must pass context from caller), brittle keyword matching
- Confidence: MEDIUM (keyword-based systems are fragile to language variation)
- Risk: False positives from keyword matching; misses nuanced context

Option C: HYBRID APPROACH
- Gemini handles inference in prompt (preferred path)
- If Gemini returns ambiguous time, apply hardcoded heuristics as fallback
- Implementation: Gemini tries first; parseTime() gets educated guess if Gemini can't decide
- Pros: Combines Gemini's NLU with deterministic fallback
- Cons: More complex, two layers to maintain
- Confidence: HIGH (leverages best of both)

Option D: ASK USER (SAFE FALLBACK)
- Implementation: Return ambiguous-time error; Calendar Scout asks user to clarify
- Signature: Keep parseTime() as-is, change consumer to show "Did you mean 3:30 AM or PM?" dialog
- Token cost: NONE
- Latency impact: Adds round-trip for user response
- Pros: Zero false positives, transparent
- Cons: Friction (user must respond), slows workflow
- Confidence: 100% (foolproof)

RECOMMENDATION
==============

PRIMARY: Option A (Gemini-Based Inference)

Rationale:
1. Gemini already has full email context; no additional API calls needed
2. LLM can handle linguistic nuance (e.g., "after school" → PM) better than keyword matching
3. Can explain its reasoning (higher user trust)
4. Token cost is negligible (~20% overhead, <$0.01/email at current Gemini pricing)
5. Can refuse ambiguous cases gracefully (return with DateConfidence="low" if unsure)

Implementation Steps:
1. Modify gemini.ts prompt (around line 47) to add:
   "If a time like '3:30' appears without am/pm, infer AM/PM from email context if possible.
    Use keywords like 'afterschool', 'pickup', 'dismissal', 'breakfast', 'lunch', 'dinner', 
    'evening', 'morning' to guide inference. If confident (>75%), add the suffix. 
    If unsure, return the time as-is and set DateConfidence to 'low'."

2. Update parseTime() to ACCEPT ambiguous times IF DateConfidence="low":
   - Reject with error if DateConfidence="high" and time is ambiguous
   - Accept bare time (treat as "needs user confirmation") if DateConfidence="low"

3. In email report, flag ambiguous times: "Time unclear: 3:30 (am or pm?)"
   Link to one-click correction dialog

SECONDARY: Option D (Ask User) for v2
- If Gemini inference underperforms (>5% false positive rate in production)
- Keep as safe fallback

AVOID: Option B (hardcoded keyword matching alone)
- Fragile, language-dependent, hard to maintain
- LLM is better suited for this task
